# Design concepts (draft, generated from concepts/design.json)

The named concepts under the Design items in `builder-inventory.md`. Deciding what the user sees and does, writing it down clearly enough to build, and watching real people use it.

Each concept has up to four checks, each counted once:

- **Know it**: says what it is and applies it on paper. Evidence: final exam questions on the concept,
  all three types (know it, use it, predict it), and `/learn` checks. Self-rated in the survey until
  the exam. (The exam's "use it" questions are scenarios on paper; the profile's "Used it" is real work.)
- **Used it**: used it in their own work. Evidence: the `/sprint-review` session scan, or the repo.
- **Built it**: built their own. Evidence: a file they wrote, committed in a shared repo.
- **Shipped it**: made it for real users and chose it on purpose (the inventory's level 5 rules).

A blank cell means the check does not apply to that concept. Evidence rules from
`builder-inventory.md` apply.

## G2 Visual fundamentals

| Concept | Used it | Built it | Shipped it | Chapter |
|---|---|---|---|---|
| **DE06 Visual hierarchy and one primary action.** Size, weight, contrast, spacing and position rank what is on the screen. Each screen gets one primary action and the rest are de-emphasized. The squint test: blur the screen; what still stands out should be the primary action. | screens with one filled primary button | a written rule such as one primary action per screen, followed in the product | n/a | Ch 5: Attention and Hierarchy |
| **DE07 Gestalt grouping.** People see items as a group when they are close together, look alike, or share a boundary. | **DE08 Fitts's law, Hick's law and cognitive load.** Fitts: a target is faster to hit when it is larger and closer. Hick: more options take longer to choose among, for a choice among unfamiliar options. Cognitive load: show what the user needs at the step where they need it, so they recognize it instead of recalling it. | n/a | n/a | n/a | Ch 5b: Fitts's law; Hick's law; Cognitive load and Jakob's law; Ch 5: Attention and Hierarchy |
| **DE09 Norman's principles and the conceptual model.** An affordance is an action a thing makes possible; a signifier is the visible cue that it is there. Mapping, constraints and feedback close the gulfs of execution and evaluation. The user's model of how the product works is built only from the system image, so a change that alters what users think the product is for needs testing first. | n/a | n/a | n/a | Ch 5b: Norman's Principles of Interaction; Ch 6: The Design Canon Behind This |
| **DE10 Typography, layout grid and color.** A short type scale, a spacing scale and a grid, and color used by meaning with one accent. | **DE11 Words are interface.** Labels, buttons and messages are instructions. Buttons are verb plus object, errors say what happened and how to fix it, names use the user's words, and confirmations say what changed. | button labels and error messages written in the user's terms | rewritten interface copy or a committed copy rule in the spec or design rules | n/a | Ch 5: Words Are Interface |
| **DE12 Accessibility baseline (WCAG).** Text contrast at least 4.5:1 (3:1 for large text), every action works by keyboard with visible focus, touch targets large enough, a label on every input, and real HTML elements so screen readers can read them. | a keyboard or contrast check run on the product | a committed accessibility rule or check result (contrast output, keyboard pass notes) and fixes that follow it | n/a | Ch 5: Accessible by Default |
| **DE13 Web, mobile, or both; mobile-first layout.** Most student products start as a responsive web app; a PWA, Capacitor, or native app is chosen for use away from a desk, device hardware, or store distribution. Mobile-first means the phone layout is the default and wider screens add columns at set breakpoints, with touch targets sized for a thumb. | the product checked at phone and desktop widths | a responsive layout or a spec for mobile behavior, committed | platform chosen in a decision record naming the alternatives, and real users reach it on that platform | Ch 5: Web, Mobile, or Both; Making Your App Mobile-Responsive |

## Book gaps

- Writing a flow down (G1 level 4): Ch 5 teaches mapping a flow but gives no file convention. Add a short 'Write the flow in the spec' block to Ch 5: Flows Before Screens, and a Flow and states section to the spec template in Ch 6b.
- Session notes (G6 level 4): Ch 6 says to take notes but gives no note format or where to commit it. Add a one-page session note template to Ch 6: Running a Usability Test.
- Changing a spec after shipping (G4 level 5): Ch 6b does not teach recording what changed in a spec and why. Add a 'When the spec changes' subsection after The Agent Team Kit's spec and build-spec Skills.
- Choosing a design system on purpose (G3 level 5): Ch 5 recommends shadcn/ui but does not show a decision record comparing options. Add an example to Decide Once.
- Recruiting test participants and consent: one line in Ch 6 (Before the Session). Thin for a step most students find hardest.
- Dark patterns and design ethics (deceptive defaults, confirm-shaming, hidden cancellation): not taught. A short section would fit after Words Are Interface in Ch 5.
- Onboarding and first-run design beyond the empty state: thin. Could extend Ch 5: Off the Happy Path.

## Evidence a packet or the session scan cannot see yet

- States (DE02): a packet sees code and nine Loom frames, which usually show the happy path. An empty, loading or error state is confirmed only if the spec lists the states or the Loom shows one. Asking for a Flow and states list in the spec would make it visible.
- Flow written down (DE01): several Sprint 2 flows exist only in code (a Steps component, a route list). The coder cannot tell a route list from a flow. A named spec section would settle it.
- Design rules (DE10, DE12, DE15): rules sometimes live only in commit messages or code comments, and contrast and keyboard checks leave no record unless output is saved. A committed check result (contrast numbers, a keyboard-pass note) would make them checkable.
- Design system reuse (DE14): counting the screens that use a shared component needs a code search the packet does not include. Adding import counts per shared component to the packet would make 'three or more screens' checkable.
- Spec text (DE18 to DE22): packets often drop spec texts under the text budget, so acceptance criteria and decisions sections cannot be read. Commit order still settles 'before the code'. Giving spec files priority in the packet would fix it.
- Design direction (DE23): directions to an agent are in the user's prompts, which the session scan reads but does not classify. Directions to a teammate or another tool (Cursor) are not visible. A scan count of prompts with a screenshot attached, or naming an element and a principle, would help.
- Usability testing (DE27 to DE29): one record may meet G5 and G6; it counts for each only when it meets each statement on its own. Session note texts are often absent from the packet.
- Know it: DE10 (typography, grid, color), DE15 (design rules for the agent), DE17 (user stories), DE19 (PRD), DE20 (spec-driven development) and DE22 (punch list and check sheet) have no exam question.
