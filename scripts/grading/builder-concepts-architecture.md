# Application Architecture concepts (draft, generated from concepts/architecture.json)

The named concepts under the Application Architecture items. What runs where, what the app remembers, who may see what, and how a change goes live safely.

Each concept is measured in up to two ways:

- **Know it** (every concept): the exams. Midterm and final questions on the concept come in three
  types (know it, use it, predict it). The September survey self-rating stands in until the midterm.
- **Practice** (every concept not marked knowledge only): the student's own work shows it, counted
  once. The **Practice** column says what counts as evidence: the `/sprint-review` session scan's
  "Builder tools you used" list, or a file in a shared repo. This is the breadth half of the profile's
  practice score; depth (`depth-levels.md`) is assigned per axis, not per concept.

A concept marked **knowledge only** has no practice check: it is measured by the exams alone.
Evidence rules are in `concept-coder.md` and `depth-levels.md`.

## A2 Data and schema

| Concept | Practice | Chapter |
|---|---|---|
| **AA09 Tables, keys and relationships.** A table is a noun of the product, a row one instance, a column one fact with a type. A primary key identifies a row; a foreign key on the many side links two tables. Facts are stored once. Only a file or database outlives the session; page memory and local storage do not. | A committed migration or schema file that defines tables with keys, which the product reads or writes. | Ch 8: Design the Data Model First. Ch 9c: Where an App Keeps Data |
| **AA10 Migrations and schema changes.** A migration is a file that makes one schema change, applied in order and kept in git. Changing a table that holds real rows means migrating them, and a rollback does not undo data, so add before you remove. | A committed migration or schema file that adds or changes a table, which the product reads or writes, or one that imports existing data. | Ch 8: Design the Data Model First (Migration). Ch 9: Rolling Back a Bad Deploy |
| **AA11 Queries and joins.** SELECT, WHERE, ORDER BY, LIMIT and JOIN. A join drops rows with no match unless it is a LEFT JOIN; an update or delete with no WHERE changes every row; a query that matches nothing returns an empty list. An index makes reads on a column fast. | A committed SQL query or query-builder call with a filter, an ordering or a join, which the product runs. | Ch 8: Asking the Database a Question |

## A3 Sign-in and access

| Concept | Practice | Chapter |
|---|---|---|
| **AA12 Authentication versus authorization.** Authentication proves who a user is. Authorization decides what that user may do to each row, and it holds only where the user cannot reach: the server or the database, never a hidden button. Permissions never come from model output. | knowledge only (exams) | Ch 7: Who You Are, What You May Do |
| **AA13 Sign-in and sessions.** Sign-in by password, a provider (OAuth) or a magic link gives the browser a signed token that every later request carries. The token expires and must never go in logs, chats or prompts. | Sign-in (a password, a provider, or a magic link) built in committed code. | Ch 7: Who You Are, What You May Do. Ch 7: Three credentials: publishable key, token, secret key |
| **AA14 Row-level security.** Policies in the database that decide which rows each request may touch, as if a WHERE were added to every query. With security on and no policies, every read returns an empty list, not an error. | A committed row-level security policy, or a server-side ownership check, that stops one user from reading or changing another user's rows. | Ch 8: Row Level Security: Enforce Access Where the Data Lives |
| **AA15 Permission tests.** A test that signs in as one user, with the publishable key, and asks for data that user must not see. It keeps the access rules true as an agent changes the code. | A committed test that signs in as one user and checks that another user's data is refused, with a record that it ran. | Ch 9b: Kinds of tests (permission tests). Ch 8: Row Level Security: Enforce Access Where the Data Lives |
| **AA31 Your endpoints are public.** Anyone can send a request to a route or a Server Action directly, with any body, signed in or not. Before it does any work, each one checks who is calling and whether the record named in the request is theirs. A route that queries as the signed-in user keeps row-level security; a route that uses the secret key skips it and must check ownership itself. | A committed route or Server Action that checks the signed-in user and then either queries as that user, so row-level security applies, or checks in code that the record belongs to the user before acting. | Ch 8: Your Endpoints Are Public |

## A5 Secrets, privacy and security

| Concept | Practice | Chapter |
|---|---|---|
| **AA21 Environment variables.** Settings kept outside the code, in .env.local and the host's settings, set separately for each environment. In Next.js only names starting with NEXT_PUBLIC_ reach the browser, so a secret never gets that prefix. | Committed code that reads secret keys from environment variables, with .env files listed in .gitignore. | Ch 8: Secrets and Sensitive Data. Ch 7: The Files in a Next.js Project. Ch 11: Where the Call Lives |
| **AA22 Publishable key, token and secret key.** The publishable key is public and can reach only what row-level security allows; a token identifies one signed-in user and expires; the secret key bypasses the rules and stays on the server. | Committed code that uses the publishable key in browser code and reads the secret key only in server code. | Ch 7: Three credentials: publishable key, token, secret key; Supabase Introduction |
| **AA23 A leaked secret.** A key committed to a public repository is published. Deleting it from the code does not help, because history keeps it: create a new key, revoke the old one, then fix .gitignore. | A commit that removes a committed secret together with a record that the key was rotated, or a secret scan of the repo with its output saved. | Ch 8: Secrets and Sensitive Data (Rotate a leaked key). Ch 7: The Files in a Next.js Project (Not in git) |
| **AA24 Sensitive data and where it may go.** Personal, student and client data may go only where its rules allow. Sending it to a model, a log or an analytics event copies it to that company's servers, so send the least the task needs. | Protections for data about people (a consent note, a redaction step in code, or access limits) written down in a committed file and applied in the product or the student's research files. | Ch 8: Secrets and Sensitive Data |
| **AA25 Keep untrusted text as data.** Text from users, other services and models is data: show it as text and pass it to the database as a value. Joined into a SQL string it becomes SQL injection, which parameterized queries prevent; inserted into the page as HTML it becomes cross-site scripting, which React prevents by default until dangerouslySetInnerHTML, Markdown with raw HTML, or a user-supplied link turns that protection off. Model output counts as untrusted text. | A committed defense against SQL injection or cross-site scripting (a query that passes user text as a value in place of joined SQL, a link allow list, a sanitizer, or rendering that replaces dangerouslySetInnerHTML or rehype-raw), with the attack named in the code, a commit message or a record. | Ch 8: Keep Untrusted Text as Data |
| **AA32 Limits on paid calls.** A route that calls a paid API, such as a model, spends money for whoever calls it. Cap each user's calls in code and answer 429 past the cap, and set a monthly spend limit on the provider account, which holds even if the code has a bug. | A committed per-user limit on a paid call (a count checked before the call, answering 429 past the cap), or a committed record of the monthly spend limit set on the provider account. | Ch 8: Your Endpoints Are Public. Ch 11: What It Costs |
| **AA33 Accounts, repository and packages.** The accounts that hold the keys (GitHub, the host, the database, the model provider) need two-factor sign-in. GitHub push protection blocks a push that contains a recognized key; Dependabot and npm audit report packages with known vulnerabilities. A package name a model suggests may not exist, or may belong to an attacker, so check it before installing. | A committed Dependabot configuration (.github/dependabot.yml), or saved npm audit output together with a commit that fixes what it reported. | Appendix: Engineering Checklist (Security) |

|---|---|---|

A branch builds a change without touching main; a pull request runs the checks, builds a preview and gets a review of the diff before the merge. ## Book gaps

- Deploying is taught in Ch 2 (Deploying a Prototype; Deployment with Vercel / GitHub Pages), both marked MOVE. Move them to Ch 7 after Tech Stacks, and add how to pick a host for a Python app (Streamlit, Render, PythonAnywhere) and what a build log is.
- Integrations with other services (OAuth connections on a user's behalf, webhooks, offering an API) are not taught. Ch 8 after Requests Are Contracts That Fail.
- Protections for data about people (consent, redaction, pseudonymizing interview or research data) are taught only as 'where data may go'. Ch 8: Secrets and Sensitive Data needs a part on consent and redaction, since A5 level 5 asks for them.
- Importing existing data (a spreadsheet or old system into tables, with duplicates removed) is not taught, though A2 level 4 counts it. Ch 8 after Design the Data Model First.
- Data and schema assume Supabase. Many products store data in SQLite, an ORM schema or a platform's own store. Ch 8 should say what counts as a defined schema in those stacks.
- Where an app keeps data (page memory, local storage, database) is only in the Ch 9c appendix. Ch 8 should open with it.
- Accounts, repository and packages (AA33) is taught only as a list of checks in the Engineering Checklist's Security section. A short passage in Ch 9 (version control) would give it a chapter home.

## Evidence a packet or the session scan cannot see yet

- A link check of 200 shows the address answers, not that this sprint's commit is what is deployed. A deployment id or commit SHA from the host (or a /version endpoint) would show it.
- Environment variables set on the host are not visible, so a feature that needs a key may not run in production. A smoke test of the live feature, saved, would show it.
- Migration, schema and row-level security texts are often absent from the packet; only file names are listed. Include the text of migrations and schema files changed this sprint.
- Test and CI runs leave no record unless the student commits output. The GitHub Actions run history for the repo would show runs and results.
- Pull requests are listed without saying whether the branch holds code or only plans, or whether they were merged by the due date. The packet should list each PR's changed files and merge date.
- A secret removed from the latest commit is still in history. A secret scan over the full history (for example gitleaks) would cover it.
- Whether outside users sign in (depth level 4, Delivered, through A3) needs a count of sign-ins from the auth table, dated. The packet cannot see it today.
- Private code repos and non-web distribution (an App Store release) are not visible to the link check or the repo scan.
- The session scan can show practice evidence for this axis from commands: build and deploy commands, git branch and gh pr, migration commands, test runs, and log reads.
